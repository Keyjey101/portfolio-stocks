# 10. Улучшения относительно оригинала (и чем обоснованы)

Всё ниже — отличия реплики от stock-llm. Остальное воспроизводится как описано.

## 1. Русский как единственный язык выводов

В оригинале LLM-тексты локализуются инструкцией при `?lang=ru`, но детерминированные
строки (`valuation_framing`, `assumptions`, фоллбек-тексты, тексты фаз) остаются
английскими всегда. В реплике:

- LLM-инструкция «отвечать по-русски» включена постоянно (`05`, §5.2);
- все кодогенерируемые строки сразу пишутся на русском (в т.ч. framing, фоллбеки,
  ошибки сканера «Скан прерван: нехватка памяти…» — так в оригинале уже сделано);
- UI-словарь ru-first; enum-значения (verdict, moat_type, …) остаются английскими
  в JSON — перевод только на отображении (сохраняет сортировку/сравнимость и
  упрощает парсинг тестами).

## 2. Один источник схемы БД

Оригинал: 55+ таблиц описаны дважды (backend `schema.sql` ~1200 строк и agents
`shared/schema.py` ~1100 строк), синхронизируются вручную — постоянный источник
расхождений. Реплика: одна миграционная цепочка (например, pydantic-модели →
SQL-миграции), обе стороны читают одну схему.

## 3. Кэш прескрин-данных (главный перформанс-фикс)

Оригинал при каждом скане заново опрашивает yfinance по всей вселенной (~770–2000
тикеров, 2 воркера) — это часы при 429-паузах и главный источник «скан завис».
Реплика: таблица `ticker_quick_cache(ticker, info_json, fetched_at)`, TTL 12 ч
(котировка/объём можно освежать чаще — split TTL: метаданные 7 дней, цена/объём
при скане). Скан с холодным кэшем — как в оригинале; с тёплым — минуты.
Обязательно: инvalidation поorporальному событию (сплит/делистинг) не требуется
при 12-часовом TTL.

## 4. Полное исключение CPP-конуса (30-дневный прогноз цены)

По решению владельца продукта прогностический конус в реплику **не переносится
вообще**. В оригинале он состоял из: ML-сервиса CPP (`/cpp/v13/predict`), карточки
«Lens B» на странице анализа и growth-типа сканера — всё это исключено. Обоснование:

- конус никогда не участвовал в фундаментальной оценке и вердикте (жил отдельной
  карточкой), т.е. на решение «переоценена/недооценена» не влиял;
- это самая тяжёлая зависимость оригинала (отдельный ML-сервис, калибровка E1–E5
  для защиты ответа от выбросов) при нулевой ценности для 3–5-летнего горизонта
  решения;
- growth-скан целиком строился на конусе и без него смысла не имеет.

Если в будущем понадобится скрининг растущих компаний — его разумно делать как
фазу-2 по аналогии с undervalued, но на фундаментальных метриках роста
(CAGR выручки/EPS, качество баланса, тренды маржи), без прогнозных моделей цены.

## 5. `POST /scan` — JSON body вместо query-string

Оригинал передаёт параметры скана urlencode'ом в query (включая списки) —
хрупко и не типизируется. Реплика: JSON body (контракт в `08`).

## 6. Фикс счётчика `undervalued` в статистике скана

В оригинале `stats.buy_count` считает вердикты `Buy/Strong Buy`, которых у
обогащённых строк физически не бывает (вердикты `STRONGLY UNDERVALUED`…), поэтому
«Undervalued: N» в UI почти всегда занижен/нулевой. Реплика: считать строки с
вердиктами `*_UNDERVALUED`.

## 7. Удаление мёртвого кода dividend-ветки в value-сканере

В `equity/scanner.py` оригинала осталась dividend-логика в `_passes_filter/_score`,
которая недостижима (роутинг уводит `scan_type=dividend` в отдельный модуль).
Реплика: сканерные типы — строго отдельные модули без общих ветвлений по типу.

## 8. Схема-первичность и кодогенерация типов

Оригинал маппит snake_case → camelCase вручную в бэкенде (~100 полей, включая
forward-compat поля, которых сканер не отдаёт). Реплика: pydantic-схемы Python —
единственный источник; TS-типы фронтенда генерируются из них (openapi-typescript
или аналог). Маппер остаётся только как слой именования, без ручных списков полей.

## 9. Наблюдаемость

- Структурные логи каждого шага: `{step, ticker, duration_ms, degraded, llm_ms}`;
  для скана — `{phase, batch, fetched, failed}`.
- Экспорт счётчиков (Prometheus/простой JSON-эндпоинт): длительности шагов, доля
  фоллбеков LLM, доля `no_estimate`, 429-паузы. В оригинале этого нет, а без него
  невозможно понять, почему «анализ стал медленным».
- Сохранять `analysis_outcomes` и раз в неделю показывать в админке направленную
  точность вердиктов (7д/30д) — дешёвая валидация всей системы (в оригинале таблица
  пишется, но не потребляется).

## 10. Кредиты — модуль с интерфейсом

Интерфейс `Billing { spend, refund }` с двумя реализациями: `NoopBilling` (по
умолчанию) и `CreditBilling` (транзакционный, как в оригинале). Контракты API не
меняются; возвраты/`settled`-логика описаны в `08`, §8.4.

## 11. Мелкие упрощения без потери поведения

- SSE `/scan/:id/progress` не реализовывать (фронтенд использует поллинг `/status`
  каждые 2 c — этого достаточно; эндпоинт в оригинале тоже не используется).
- Дублирующаяся палитра в стилях страницы анализа оригинала (второй набор
  hardcoded-цветов поверх дизайн-токенов) — в реплике только токены (`07`, §7.3).
- `fetch_quick` двухступенчатый (fast_info → info) сохранить — это реальная
  экономия на прескрине; добавить к нему кэш из §3.
